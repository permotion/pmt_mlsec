## Hypothesis

v5 identified that 51% of remaining FPs are POSTs without payload indicators. The model confuses them with attacks due to high `content_length` and `content_param_count`. Candidate feature: `content_param_density` = `content_param_count / content_length` — parameter density relative to body size.

---

## POST subpopulation analysis

Correlations calculated **exclusively on the 17,580 POST requests** (28.8% of the dataset, where body has real meaning):

| Feature | POST correlation | Global correlation | Signal |
|---|---|---|---|
| `content_param_density` | **-0.216** | +0.066 | ✅ Negative signal — attacks have lower density |

The correlation is **negative**: malicious POSTs have lower `content_param_density` than normal ones. This indicates that in POST attacks the parameter values are longer (injected payloads) → fewer equals per body character.

### POST distribution — normal vs attack

| Statistic | Normal POST | Attack POST |
|---|---|---|
| Median | 0.0633 | 0.0533 |
| Mean | 0.0837 | 0.0604 |
| P75 | 0.0789 | 0.0714 |
| P90 | **0.2500** | 0.0820 |
| P95 | **0.2500** | 0.1667 |

Normal POST traffic has a P90 of 0.25 — short forms with many `=` relative to body. POST attacks rarely exceed 0.17 (P95). Separation exists but distributions overlap significantly in the 0.04–0.08 range.

## Analysis

### Real signal, marginal impact

The feature has -0.216 correlation in POST and the model uses it (rank 6). The impact was +0.0007 Precision, -5 FPs. The signal exists but normal POST and attack POST distributions overlap too much in the 0.04–0.08 range for the model to separate case by case.

### The limit of body structural features

The remaining 938 FPs (98.6% without payload indicators) cannot be separated with currently available columns alone. The project has exhausted extractable signal from:
- URL length and structure (`url_length`, `url_path_depth`, `url_query_length`, etc.)
- Body length and structure (`content_length`, `content_param_count`, `content_param_density`)
- Keyword indicators (`url_has_pct27`, `content_has_script`, etc.)

To reduce structural FPs, **new information** from the raw CSV is needed — columns discarded in EDA that might have specific signal for this subpopulation.

## Raw CSV inspection — root cause of FPs

Script: `notebooks/experiments/csic2010_fp_analysis_v6.py`

The exact v6 model (threshold=0.2903, FP=938) was reproduced, original indices of test set FPs were identified and cross-referenced with the raw CSV to see actual content.

### Headers hypothesis — discarded

Before inspection it was expected that `content-type` or `cookie` would have signal:

| Header | FP | TN | Conclusion |
|---|---|---|---|
| `cookie` | 100% have cookie | 100% have cookie | ❌ Doesn't discriminate — all dataset requests have cookie |
| `content-type` | 481 `application/x-www-form-urlencoded` + 457 NaN | 711 `application/x-www-form-urlencoded` + 3751 NaN | ❌ NaN is simply GET (no body) — no difference between FP and TN of same method |

Headers discarded in EDA have no signal for this problem. Cookie is constant across the entire dataset.

### Root cause — encoding confusion

When inspecting actual content of **high confidence FPs (proba > 0.70)**, the pattern is immediately obvious:

```
FP  proba=1.000  POST
content: modo=registro&login=tanchak&apellidos=Murgu%EDa+Aversa
         &email=wendell%40somosagelespa%F1a.com

FP  proba=1.000  POST
content: modo=entrar&login=clipsham5&pwd=lIMpi%24a%FA%F1as

FP  proba=0.999  POST
content: modo=registro&login=jamaly&password=exageraci%F3%3Fn
         &apellidos=Cruzado+Garmes

FP  proba=0.930  POST
content: modo=registro&apellidos=D%27Amico+Urrea

FP  proba=0.917  POST
content: modo=registro&nombre=Enrique&apellidos=Objio
         &password=escusa%F1a
```

These are **legitimate forms from a Spanish store** with names, surnames and passwords containing accented characters encoded in ISO-8859-1/Latin-1.

### Why the model classifies them as attacks

The model has `content_pct_density` as the second most important feature (importance 959). This feature counts **all** `%XX` in the body, without distinguishing type. For the model, `%F1` (n-tilde) and `%27` (') produce exactly the same signal.

**The distinction the model cannot make with current features:**

| Type | Hex range | Concrete examples in FPs | Real meaning |
|---|---|---|---|
| **Harmless Latin-1** | `%C0`–`%FF` | `%ED`=i-acute, `%F1`=n-tilde, `%FA`=u-acute, `%F3`=o-acute, `%E1`=a-acute | Spanish accented vowels |
| **Harmless Latin-1** | `%40`–`%7E` | `%40`=@, `%24`=$, `%2B`=+ | Symbols in emails and passwords |
| **Attack** | `%00`–`%3F` | `%27`=', `%3C`=<, `%3E`=>, `%3B`=; | SQLi / XSS chars |

Real attacks **never encode n-tilde or a-acute** — they have no reason to include Latin-1 characters in an injection payload. Legitimate traffic from a Spanish store **always has them** in names and passwords.

### The edge case — D'Amico with %27

The surname `D%27Amico` uses `%27` for the apostrophe — exactly the same encoding SQLi uses for single quote. There are 5 FPs with `%27` in the content (out of 938 total). These are **unavoidable** with text features unless full parameter context is analyzed (the `%27` appears in the value of `apellidos=`, not in a SQL construct). They are 0.5% of FPs — don't move the needle.

### Quantifying the problem

| FP Segment | Amount | % | Cause |
|---|---|---|---|
| High confidence (proba > 0.50) | 568 | 60.2% | Forms with dense Latin-1 encoding — model is very convinced |
| Low confidence (proba ≤ 0.50) | 375 | 39.8% | Forms with less Latin-1 encoding — close to threshold |
| With `%27` in content | 8 | 0.9% | Surnames with apostrophe (D'Amico, O'Brien, etc.) |
| Without any suspicious keyword | 938 | **100%** | None have real SQLi/XSS — all are structural FPs |

### The gap is closable

The root cause is precisely identified: `content_pct_density` does not distinguish Latin-1 encoding from attack encoding. The solution is a feature capturing specifically the proportion of Latin-1 in the body:

**Candidate feature for v7:** `content_pct_latin1_density` = proportion of `%[CcDdEeFf][0-9A-Fa-f]` sequences in body (code points U+00C0–U+00FF — accented characters, n-tilde, u-diaeresis, etc.)

- **Expected correlation:** strongly positive with normal POST traffic (Spanish forms), close to zero with attacks — for three concrete technical reasons: (1) SQLi/XSS payload must be interpreted as valid code by the server, and a SQL parser doesn't expect `n-tilde`; (2) attackers use minimal and precise payloads — unnecessary characters only add detection surface; (3) Latin-1 encoding can corrupt the payload if the server interprets it as ASCII or UTF-8. In the CSIC 2010 dataset: **zero attacks have `%F1` or `%ED`**, 100% of requests with `%F1` are legitimate forms.
- **Expected impact:** the 568 high-confidence FPs are mostly forms with dense Latin-1 encoding → this feature should allow the model to revert those predictions
- **GET equivalent:** `url_pct_latin1_density` — same logic applied to URL, for the 461 GET FPs
