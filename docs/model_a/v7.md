## Hypothesis

Raw CSV inspection in v6 identified that FPs are forms with Spanish names and passwords using Latin-1 encoding (`%F1`=n-tilde, `%ED`=i-acute, `%FA`=u-acute). It was expected that attacks would not have Latin-1 — and that this asymmetry would be the missing signal.

**Candidate features:**
- `content_pct_latin1_density` = proportion of `%[CcDdEeFf][0-9A-Fa-f]` in the body
- `url_pct_latin1_density` = proportion of `%[CcDdEeFf][0-9A-Fa-f]` in the URL

### Why the hypothesis failed

CSIC 2010 attacks were generated against a Spanish store. The attack generator builds requests with Spanish parameters in the **field names** — even if the parameter *value* contains the injection payload, the rest of the body has accented characters at the same rate as a normal request:

```
# POST attack — "apellidos" field has Latin-1, "pass" value has the injection
apellidos=Garc%EDa&pass=%27+OR+1%3D1--&email=test%40test.com
```

The generator does not distinguish between what part of the request is the payload and what part is context. That's why the Latin-1 distribution in POST is practically identical between normal and attack (mean 0.00420 vs 0.00413).

For `url_pct_latin1_density` the correlation is **positive** in GET (+0.131): GET attacks have *more* Latin-1 in the URL than normal traffic — in the opposite direction than expected. Parameter tampering attacks include values with Spanish characters in the query string.

### Distributions — confirm total overlap

| Statistic | Normal POST | Attack POST |
|---|---|---|
| Mean | 0.00420 | 0.00413 |
| Median | 0.000 | 0.000 |
| P90 | 0.01471 | 0.01389 |
| P95 | 0.01587 | 0.01562 |

Distributions are practically identical. There is no separation the model can exploit.

## Analysis — current approach limit

### ROC-AUC continues to improve

LightGBM v7: ROC-AUC 0.9677 (+0.0016 vs v6). The model's separation capacity increased. But that improvement does not translate to fewer FPs at the current threshold because the model cannot find a cutoff point that simultaneously improves Recall and Precision.

### The 936 FPs are structurally ambiguous

After v5, v6 and v7, the pattern is clear: the remaining FPs are normal requests that the model cannot differentiate from attacks with available dimensions:

| Analyzed dimension | Result |
|---|---|
| URL/body length and structure | Explored since baseline — exhausted signal |
| Keyword indicators (`%27`, `SELECT`) | 98.6% of FPs without any |
| Query string structure (`url_path_depth`, `url_has_query`) | Improved in v4, exhausted |
| Parameter density (`content_param_density`) | Real but marginal signal |
| Latin-1 vs attack encoding | No separation — attacks also have Latin-1 |
| HTTP headers (`cookie`, `content-type`) | No signal — constant in the dataset |

### What closing the gap completely would require

To separate the 936 FPs from TNs, information not captured by current features would be needed:

1. **Semantic analysis of parameter values** — not just if there is `=` or `%27`, but what is in the value of each parameter. Requires parsing the body as `key=value&key=value` and analyzing each value individually.
2. **Session-level features** — is this request part of a coherent navigation sequence? Automated attacks have different session patterns.
3. **Frequency and rhythm** — scanners send requests at regular intervals; normal traffic has variability.

These dimensions require a different approach than feature engineering over individual HTTP fields.

---

## Decision

Latin-1 features have practically zero correlation in the relevant subpopulation and wrong direction in the other. **They are not incorporated into official preprocessing.**

### Options for v8

1. **Accept 0.79 Precision as practical ceiling of current approach** and move to Model B. The MVP requires 0.85 but 0.79 with 0.95 Recall can be a valid starting point for production with manual alarm review.

2. **Semantic body parsing** — extract individual POST parameter values and build features over values (value length, special chars ratio in value). Higher implementation complexity.

3. **CSIC 2010 dataset analysis** — verify if the 936 FPs have any pattern in fields we haven't explored yet (User-Agent, Accept-encoding, or number of parameters in URL vs in body).
